## 2. Qué se reparó hoy, con evidencia

### 2.1 StarHome OS servía código obsoleto (bug real, reparado)

El servicio `systemd --user starhome-os.service` llevaba corriendo desde las
19:02:19 (arrancado antes de los commits K17-K19, que aterrizaron entre
19:54 y 20:26). Por eso `/api/dashboard/content`, `/api/dashboard/accounting`
y `/api/dashboard/business/cass` devolvían **404** pese a existir el código en
el repo (`cano_hermes/api/app.py:621,805,902`).

- **Evidencia antes**: `curl localhost:8787/api/dashboard/content` → 404.
- **Reparación**: `systemctl --user restart starhome-os.service`.
- **Evidencia después**: las 6 rutas responden 200 (sección 3).
- No fue necesario ningún cambio de código — el bug era operativo (servicio
  no recargado), no de fuente.

### 2.2 PR #1 de `cano-adaptive-content-skill` mergeado

- Verificado antes de mergear: `mergeStateStatus: CLEAN`,
  `mergeable: MERGEABLE`, CI (`validate` x2) en `SUCCESS`, head en
  `256ff0b` (el mismo commit validado por el comentario del owner en el PR),
  49/49 tests verdes en checkout local propio.
- El propio PR trae un comentario del owner con instrucción explícita de
  merge: *"merge this PR using Squash and merge, not a regular merge
  commit"*.
- Este protocolo (K16, a diferencia de Prometeo) autoriza explícitamente
  mergear el propio trabajo cuando se cumplen esas condiciones — se cumplían,
  se mergeó: `gh pr merge 1 --squash` → commit `f73f434` en `main`.
- Post-merge: `main` actualizado, `pytest -q` → 49/49 sigue verde.
