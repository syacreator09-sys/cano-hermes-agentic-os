## 1. Patrón elegido para detectar `orden:`

```
^\s*orden\s*:\s*(.+)$          (case-insensitive, DOTALL)
```

- Coincide con `orden: ...`, `Orden:...`, `ORDEN : ...`, y un mensaje
  multilínea cuya primera línea abre así.
- **No** coincide con una mención de "orden" a mitad de frase (p.ej.
  "necesito una orden de compra") — solo dispara si el mensaje *abre* con
  el token, evitando falsos positivos sobre conversación normal.
- Se prefirió sobre sintaxis de slash-command (`/orden ...`) porque
  Telegram ya reserva `/` para comandos que el propio gateway puede
  interceptar antes de que el skill vea el texto.
- Es deliberadamente simple: el agente (que es un LLM leyendo el mensaje)
  lo reconoce leyendo el texto, sin necesidad de ejecutar un script de
  regex.
- Presupuesto por defecto cuando el operador no da uno:
  `max_cost_usd = 2.0` — razonado en detalle en el propio SKILL.md (orden
  de magnitud de `default_daily_budget_usd=5.0` sin agotar el día en una
  sola orden, y por encima del piso de prioridad 0 del bridge).

Archivo real: `~/.hermes/skills/starhome-orders/SKILL.md` (fuera de este
repo, mismo patrón de directorio que cualquier otro skill de hermes-agent:
`SKILL.md` con frontmatter YAML + cuerpo markdown). Confirmado
**discoverable en vivo** tras reiniciar el gateway (`hermes gateway
restart`, PID 400582) y consultar la propia herramienta de hermes-agent:

```

## 2. CLI `order submit/status/list`

Implementado en `cano_hermes/cli.py` como nuevo subcomando `order` (mismo
estilo argparse que `forge`), más un endpoint `GET /api/orders` nuevo en
`cano_hermes/api/app.py` (no existía; K5 solo dejó `POST` y
`GET /api/orders/{id}`).

**Decisión de diseño:** las tres verbos hablan HTTP puro contra
`http://127.0.0.1:8787` (override vía `STARHOME_API_BASE`), en vez de
mezclar HTTP para submit/status con `SQLiteStore` directo para list. Esto
mantiene al CLI ejecutando exactamente la misma superficie que usará el
skill de Telegram (un solo camino para crear/consultar órdenes, fácil de
testear mockeando `httpx`), a costa de una dependencia de red local que de
todos modos siempre está disponible en esta máquina (StarHome corre como
servicio systemd `starhome-os.service`).

**Evidencia real (proceso `hermes-cano` del propio venv, contra el server
en vivo, no un test):**

```
$ hermes-cano order submit "orden: confirma con un ok que el CLI de StarHome funciona end to end" --source cli --budget 0.5
{
  "objective": "orden: confirma con un ok que el CLI de StarHome funciona end to end",
  "source": "cli",
  "budget": {"max_cost_usd": 0.5, "max_turns": 12, "timeout_seconds": 900},
  "id": "order-974d7f388d3a",
  "status": "received",
  ...
}

$ hermes-cano order status order-974d7f388d3a
{... "status": "received", "tasks": [] ...}

$ hermes-cano order list | jq '[.[].id][:5]'

`order-974d7f388d3a` se dejó deliberadamente **sin dispatch** — ya se
corrieron dos ciclos completos de dispatch→kanban→agregación más abajo
(§3) y repetir un tercero solo para probar el CLI hubiera sido gasto/carga
redundante sin valor de evidencia adicional.

## 3. Demo E2E — resultado real y honesto

### Lo que se verificó de punta a punta, con evidencia real

Se corrieron **dos órdenes reales completas** directamente contra el
StarHome OS en producción (`starhome-os.service`, puerto 8787) y el
gateway hermes en producción (`hermes-gateway.service`, dispatcher
embebido, `kanban.dispatch_in_gateway=True`), sin mocks, sin dry-run:

Esto confirma, con IDs y timestamps reales, el tramo completo:
**`POST /api/orders` → dispatch → Kanban board `starhome` → dispatcher del
gateway reclama la tarea → un worker real (`hermes` subprocess, perfil por
defecto) la ejecuta y responde → hook `kanban_task_claimed`/`completed` →
`POST /api/bridge/kanban-events` (firmado HMAC, verificado) → StarHome
transiciona la orden → aggregator crea la tarea de síntesis tier-0 →
gobernanza (`PermissionEngine`, modo `supervised` real de este proceso)
exige aprobación humana antes de sintetizar → orden queda `BLOCKED` con una
`ApprovalRequest` real pendiente**.

### Aprobaciones pendientes dejadas para Cano

4 `ApprovalRequest` quedaron `pending` en `GET /api/approvals` (2

para que Cano las revise en `hermes dashboard` o `GET /api/approvals`
cuando vuelva.

## 4. Bug real encontrado y corregido durante la demo

**Síntoma:** el run 1 (`order-c334c655cf60`) terminó en `FAILED` con
`synthesis_status: "approval"` en el evento `order.failed` — una orden que
en realidad solo estaba esperando aprobación humana (un caso normal y
esperado en modo `supervised`) se reportaba como si el sistema hubiera
fallado.

**Causa raíz:** `cano_hermes/orchestration/aggregator.py`,
`close_order_with_synthesis`. El código original solo mapeaba
`TaskStatus.REVIEW` (compuerta humana *después* de correr) a
`OrderStatus.BLOCKED`; cualquier otro estado no-DONE —incluido
`TaskStatus.APPROVAL` (compuerta humana *antes* de correr, la que dispara
`PermissionEngine` bajo `execution_mode=supervised`, el modo real de
producción de esta máquina)— caía al `else: OrderStatus.FAILED`. El propio
docstring de `dispatch_order` en `api/app.py` ya documentaba que `BLOCKED`
es exactamente para "esperando una compuerta humana genuina" — el bug era
que el aggregator no había contemplado que esa compuerta puede llegar
*antes* de ejecutar, no solo después.

**Fix:** `OrderStatus.BLOCKED if refreshed.status in (TaskStatus.REVIEW,
TaskStatus.APPROVAL) else OrderStatus.FAILED` (ver comentario extendido en
el propio archivo, con el order id real de esta demo como referencia).

**Verificado en vivo, dos veces:** run 1 (antes del fix) → `FAILED`; se
reinició `starhome-os.service` con el fix; run 2 (después del fix, mismo
flujo, misma orden trivial) → `BLOCKED` correctamente.

**Test de regresión añadido:**
`tests/test_k7_kanban_events.py::AggregatorUnitTests::
test_synthesis_needing_approval_blocks_order_not_fails_it` — monkeypatchea
`execution_service.run` para dejar la tarea de síntesis en `APPROVAL` (tal
como lo hace `PermissionEngine` real bajo `supervised`) y confirma
`OrderStatus.BLOCKED`, el evento `order.blocked` con
`synthesis_status=approval`, y que **no** se dispara la notificación de
`order_done` (BLOCKED no es DONE).

## 7. Decisiones no triviales / bloqueos reales

- **No hubo bloqueos externos** (no gates de Cano, no credenciales
  faltantes) — StarHome API y el gateway hermes ya estaban corriendo y
  sanos al empezar.
- El **gateway se reinició** (`hermes gateway restart`) para garantizar
  descubrimiento limpio del skill nuevo — servicio systemd de usuario,
  reinicio gracioso (esperó a que terminaran turnos en vuelo), verificado
  `active (running)` y `/api/health` sano después.
- **`starhome-os.service` se reinició dos veces**: una para nada
  relacionado con este trabajo (ya estaba así al empezar la sesión — el
  log muestra un restart previo a las 16:12), y una por mí, para cargar
  el fix del aggregator (§4) antes del run 2 de la demo.
- El bug del §4 se corrigió sobre la marcha porque bloqueaba poder
  reportar honestamente qué pasa al final de una orden real bajo el modo
  de producción (`supervised`) — no es un feature nuevo, es una
  corrección de una clasificación de estado incorrecta que el propio
  código ya documentaba como intención (BLOCKED para compuertas humanas)
  pero no implementaba completo.
